# Agents / Subagents

> Один основной агент является default architecture.

Subagents разрешены только при наличии реальной причины. Следующая схема
показывает возможное расширение, а НЕ обязательную архитектуру:

```text
Main Agent
   │
   ├── optional Subagent A
   ├── optional Subagent B
   └── optional Subagent C
```

Subagent допустим, если задача хорошо изолирована, нужен отдельный контекст,
задача может выполняться независимо, декомпозиция реально снижает сложность,
а результат subagent можно валидировать. Не использовать subagents просто ради
демонстрации multi-agent architecture.

Перед добавлением определить вход/выход, критерии проверки, доступные tools,
лимиты времени/вызовов и поведение при ошибке. Основной агент отвечает за
интеграцию и проверку результата. Учесть задержку, стоимость и риск конфликтующих
действий; отдельный внутренний function/service call часто достаточен.

## Анти-паттерны

```text
Agent → Agent → Agent → Agent
```

Цепочка делегирования без необходимости и проверяемых границ задач.

```text
LLM → LLM → LLM
```

Цепочка вызовов для детерминированной задачи, которую можно выполнить обычным кодом.

Конкретные агенты и subagents до выбора кейса не создаются.
