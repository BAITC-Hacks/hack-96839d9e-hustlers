# AI Agent: архитектурный шаблон

> Архитектура должна начинаться с минимального количества компонентов и усложняться только при наличии требования кейса.

Это распределение ответственности, а не список обязательных сервисов или готовая
реализация. Стек, провайдер и конкретный агент будут выбраны после объявления кейса.

```text
User
  ↓
UI / API
  ↓
Agent Orchestrator
  ↓
LLM
  ↓
Tool Selection
  ↓
Tool Executor
  ├── Domain Tools
  ├── Retrieval Tools (optional)
  └── Action Tools (only when required)
  ↓
Tool Results
  ↓
LLM
  ↓
Final Response
```

LLM может вернуть финальный ответ без tool call. При необходимости вызовы
повторяются в пределах установленного лимита, а не в бесконечном цикле.

## Ответственность компонентов

- **UI/API:** принимает запрос и показывает результат или понятную ошибку.
  Проверяет формат и размер входа, аутентификацию/авторизацию, когда они нужны кейсу.
- **Agent Orchestrator:** управляет контекстом, запросами к LLM, разрешённым набором
  tools и завершением цикла. Задаёт лимиты шагов, времени и расхода токенов.
  Не заменяет domain services и не исполняет произвольный сгенерированный код.
- **LLM:** интерпретирует запрос, предлагает tool calls и формирует ответ на основе
  полученных результатов. Предложение модели само по себе не разрешает действие.
- **Tool Executor:** сопоставляет имя с зарегистрированным tool, валидирует вход,
  проверяет права, выполняет вызов backend-кодом и возвращает структурированный результат.
- **Tools:** небольшие контролируемые интерфейсы к необходимым возможностям.
  Domain tools обращаются к domain services; action tools выполняют разрешённые
  изменения; retrieval tools, если нужны, получают релевантные источники.
- **Domain services:** содержат детерминированные правила и вычисления вне prompt.
  Могут вызываться обычным кодом без участия LLM и тестируются независимо.
- **Retrieval layer (optional):** ищет информацию с учётом доступа, возвращает
  релевантный контекст и сведения об источниках. Способ поиска определяется кейсом.

## Границы и ошибки

Валидация выполняется на входе UI/API, перед каждым выполнением tool и внутри
domain services для их инвариантов. Проверка в UI не заменяет backend-проверки.
Неизвестные tools и недопустимые аргументы отклоняются до выполнения.

Executor преобразует ошибки tools в структурированный результат без секретов.
Orchestrator обрабатывает ошибки провайдера, timeout и исчерпание лимитов,
завершая запрос понятным статусом. UI/API показывает пользователю ошибку;
технические детали при необходимости остаются в безопасных backend-логах.
Повторы должны быть ограничены; изменяющие состояние действия нельзя слепо повторять.

Secrets читаются backend-кодом из environment variables. Локальные `.env` не
коммитятся; `.env.example` содержит только placeholders. Не помещать credentials
в UI, prompts, tool arguments/results или логи.

Один основной агент — исходная архитектура. Не вводить отдельный агент, сервис
или framework для каждой функции. Добавлять orchestration только при доказанной
пользе для выбранного кейса; см. [agents/subagents](AGENTS_AND_SUBAGENTS.md).
