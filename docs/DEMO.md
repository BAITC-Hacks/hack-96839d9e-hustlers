# Демонстрация WindOps AI

## Что готово

В репозитории находятся исходные SCADA, настоящий архив NOAA GFS, сохранённые
CatBoost-модели обеих турбин, независимая январская проверка и февральские
прогнозы. Повторное обучение для демонстрации не требуется.

Основной проверенный сценарий использует **детерминированное управление**:
погодный архив → проверка исторической доступности → CatBoost → сохранение → UI.
Это реальные прогнозы мощности, но такой запуск не демонстрирует работу LLM.

## Подготовка

Установите зависимости и создайте `config.local.json` по разделу
[«Установка и запуск» в README](../README.md#установка-и-запуск).
Для интерфейса нужны `Asia/Almaty`, нормировка `0_1` и площадки
`turbine_1`, `turbine_2`. Затем из корня проекта:

```bash
export PYTHONPATH=src
export WINDOPS_ML_MODULE=windops.ml.plugin
export WINDOPS_EXECUTION_MODE=deterministic
export WINDOPS_OFFLINE=1
.venv/bin/python -m streamlit run app.py
```

Откройте [приложение](http://localhost:8501). После установки зависимостей этот
сценарий работает без сети и OpenAI-ключа, используя `data/weather/` и `models/`.
Синтетический режим оставьте выключенным.

## Сценарий для жюри

1. **Первый прогноз.** Выберите обе турбины, дату выпуска **31.01.2026**, время
   **23:00**, горизонт **48 часов**. Нажмите «Сформировать прогноз». Ожидаются
   96 строк: 1–2 февраля, по 48 часов на турбину, в зоне `Asia/Almaty`.
   Проверьте график, почасовую таблицу и «CSV выбранного выпуска».
2. **Качество.** На вкладке «Проверка качества» загрузите
   `data/ml/january_backtest.json` и нажмите «Проверить артефакт».
   Для турбины 1 MAE ≈ 0,2156, RMSE ≈ 0,2991; для турбины 2 — 0,2206 и 0,3064.
   На каждую турбину использовано 1 464 прогнозные пары, исключений нет.
   Январские модели отделены от финальных; сравнение с baseline использует
   одинаковые пары. Метрики выражены в шкале нормализованной мощности 0–1.
3. **Происхождение.** На вкладке «Агент и данные» откройте паспорт: источник
   NOAA GFS, время погодного выпуска, историческая доступность, версия модели,
   cutoff и проверки. В этом режиме исполнитель — `deterministic`.
4. **Обновление.** Для первого выпуска нажмите «Проверить обновления».
   Backend сдвинет исторический момент на 12 часов, к **01.02.2026 11:00 +05:00**,
   и использует новый допустимый GFS. Появятся новая версия и сравнение на
   общих часах; предыдущая версия сохранится в истории. Модель не переобучается.
5. **Весь февраль.** Вернитесь на вкладку «Прогноз», раскройте «Исторический
   replay февраля». Даты означают **даты выпусков**, поэтому оставьте
   **31.01.2026–28.02.2026**. Нажмите «Запустить replay»: ожидаются **58 выпусков,
   0 ошибок**. Выгрузка всех версий содержит **2 784 строки**, включая часы марта.
6. **Один прогноз на час.** В replay отметьте правило выбора последнего
   доступного выпуска до целевого часа и скачайте «Февраль · один прогноз на час».
   Ожидаются **1 344 уникальные пары `(site_id, target_time)`**, без пропусков.
   В этом replay используются только ежедневные исходные выпуски. Для такого
   набора правило совпадает с ML-выгрузкой: день D берётся из выпуска D−1 в 23:00.

Первый выпуск от 31 января обязателен для часов 1 февраля. Выпуски конца февраля
сохраняют полные 48 часов с переходом в март.

Фактической мощности за февраль нет: февральскую ошибку не показываем.
Формат CSV является форматом команды; официальный формат сдачи нужно сверить
с требованиями организаторов.

## Проверка из терминала

В том же окружении:

```bash
.venv/bin/python -m windops.cli forecast --site turbine_1 --origin 2026-01-31T23:00:00+05:00 --horizon 48
.venv/bin/python -m windops.cli replay --start 2026-01-31 --end 2026-02-28
.venv/bin/python -m windops.ml.cli export-february
```

Готовые таблицы находятся в `data/ml/february_hourly.csv` и
`data/ml/february_full_releases.csv`. Паспорта и журналы отдельных запусков —
в `data/forecasts/<forecast_id>/`. Произвольный JSON, загруженный в UI, не получает
доверие автоматически и не становится разрешением на итоговый экспорт.

Полная проверка с настоящими моделями и сохранённым выпуском:

```bash
export WINDOPS_RUN_REAL_ML_TEST=1
export WINDOPS_SMOKE_BUNDLE=data/forecasts/forecast-3bd7a5659d75a23ee6b9aea4/bundle.json
.venv/bin/python -m pytest -q
.venv/bin/python -m compileall -q app.py src
uv pip check --python .venv/bin/python
```

Тесты могут обновлять служебные метаданные погодных наборов и отчёт интеграции.
Для проверки без изменения исходных артефактов скопируйте `data/` в отдельный
локальный каталог, задайте его в `WINDOPS_DATA_DIR` и перенесите туда же путь
`WINDOPS_SMOKE_BUNDLE`.

## Проверка LLM-демонстрации

В коде реализован один агент Responses API со строгими инструментами.
Для настоящей проверки нужны настроенные **`OPENAI_API_KEY` и `OPENAI_MODEL`**,
а также `WINDOPS_EXECUTION_MODE=agent`. Файл `.env` автоматически не читается.
`WINDOPS_OFFLINE=1` ограничивает погодные запросы; для OpenAI нужен интернет.

Проверка считается успешной после реального вызова API, выполнения инструментов
и сохранения проверенного прогноза с исполнителем `openai_responses`.
Используйте отдельный каталог приёмки с копией погодного кэша и без прежних
прогнозов: повтор существующего прогноза сохраняет его первоначальный паспорт.
Режим `auto` с переходом в `deterministic_fallback` не подтверждает работу LLM.
Ключ не нужно отправлять в чат или добавлять в Git.
