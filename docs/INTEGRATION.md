# Интеграция WindOps AI

## Фактическое состояние

Backend участника №2 реализован в `src/windops/backend.py` и поддерживает
описанный ниже протокол. Настройка: `WINDOPS_BACKEND_MODULE=windops.backend`.
Погодный архив и исходные CSV находятся в `data/` и добавлены командой в Git.
ML-модуль участника №1 реализован в `windops.ml.plugin`; команды подготовки,
обучения и проверки описаны в [ML.md](ML.md). Настоящие модели двух турбин
обучены; январский backtest и февральские прогнозы сохранены в `data/ml/`.
Единственная точка связи UI с backend — `src/windops/ui/adapter.py`.
Погодные поля, политика времени, команды и контракт модели описаны в
[BACKEND.md](BACKEND.md). Полная погодная/ML-интеграция проверяется после
подключения реального ML-модуля через `WINDOPS_ML_MODULE`.

| Возможность | Статус |
| --- | --- |
| Просмотр, графики, таблицы, паспорт, валидация | Реализованы в UI |
| Синтетический fixture | Явный режим тестирования, без итогового экспорта |
| Загрузка JSON | Просмотр непроверенного артефакта |
| Реальная архивная погода NOAA GFS | Backend реализован, проверены реальные запросы |
| ML-модель | Отдельные CatBoost двух турбин; январские и финальные версии в models/ |
| Независимые январские метрики | data/ml/january_backtest.json; 2928 реальных пар |
| Replay и проверка обновлений | Проверены 58 выпусков и историческое обновление с настоящей моделью |

## Подключаемый Python-модуль

Установите `WINDOPS_BACKEND_MODULE` в имя доступного Python-модуля команды.
Адаптер импортирует его и проверяет, что функции принимают эти именованные аргументы:

```python
run_forecast(site_id, forecast_origin, horizon_hours)
run_replay(start_date, end_date)
check_updates(forecast_id)  # необязательная возможность
```

`run_forecast` получает одну турбину, ISO-дату со смещением и горизонт 24/48;
возвращает объект со схемой bundle ниже: словарь, `ForecastBundle` или объект с
`model_dump()`. Для двух турбин UI-адаптер выполняет вызов на каждую турбину.
Группа представления сохраняет исходные `forecast_id`/`run_id` и доказательства
каждого участника; она не означает новую версию прогноза модели. Вызовы с разными
временами или режимами не объединяются в один выпуск.

`run_replay` получает `datetime.date`, возвращает
`{"bundles": [bundle, ...], "errors": [...]}`. Backend сам задаёт виртуальные часы,
шаг выпуска и архивную доступность; UI не запускает цикл альтернативных расчётов.
`check_updates` возвращает `None`/`[]`, если входы не менялись, или новые bundle
(один, список либо `{"bundles": [...]}`). Повторный `forecast_id` отклоняется.

Совместимые вызовы включаются по отдельности. Произвольная ошибка импорта или
исполнения даёт понятное безопасное сообщение и не включает синтетику.
HTTP-сервер не требуется. Модуль выбирает разработчик через окружение, а не
загружаемый JSON. Координаты, секреты провайдера и пути моделей остаются в backend.

## Предлагаемая схема выпуска

`ForecastBundle` — внутреннее представление UI из `adapter.py`, не замена будущей
общей схеме. Обязательны `forecast_id`, `rows`, `validation_summary`, `provenance`,
`report_facts`; дополнительно передаются `events`, `weather`, `horizon_hours`,
`site_ids`, `timezone`, `source_mode`, `executor`. При повторном расчёте нужны новые
`forecast_id` и `run_id`, даже если историческое время выпуска осталось прежним.

В каждой строке `rows`:

| Поле | Значение |
| --- | --- |
| `run_id`, `site_id` | Реальные строковые идентификаторы запуска и турбины |
| `issued_at` | Исторический момент выпуска, ISO 8601 со смещением |
| `target_time` | Целевой час, ISO 8601 со смещением |
| `horizon_step`, `lead_hours` | Целый шаг 1…24 или 1…48 |
| `prediction` | Конечное число в нормализованной шкале 0–1 |
| `model_version`, `weather_version`, `quality_flag` | Версии и качество |
| `p10`, `p50`, `p90` | Необязательные настоящие квантили модели |

Необязательный квантиль, равный `null` во всех строках **данной турбины**,
считается отсутствующим. Частичные пропуски внутри предоставленного ряда
этой турбины — ошибка. Одна турбина может иметь диапазон, а другая — только
точечный прогноз. Полностью пустые квантильные колонки не попадают в CSV.

Полностью пустая необязательная колонка квантиля означает отсутствие этого
квантиля и не включается в CSV. Частично пустая колонка не считается полным
квантильным прогнозом и блокирует финальную выгрузку.

`source_mode` принимает `real` (новый расчёт по реальным входам), `cached`
(сохранённый результат) или `demo` (синтетика). `executor` независимо описывает
исходного исполнителя: просмотр сохранённого результата не запускает агента.

Необязательная таблица `weather` содержит `site_id`, `target_time`, `data_kind`,
прогнозный ветер `wind_speed`/`wind_speed_mps` либо отдельно `wind_speed_10m`/
`wind_speed_100m`, температуру `temperature_c`/`temperature`/`temperature_2m`.
Для общего поля ветра высота указывается в `wind_height_m`, если известна.
Разные высоты и фактическая/прогнозная погода не склеиваются в одну линию.
В паспорте погоды дополнительно показываются `issued_at`, `run_initialized_at`,
`retrieved_at`, `availability_upper_bound`, `availability_basis`, если предоставлены.
`events` — список реальных событий backend; UI не создаёт журнал или длительности.

`timezone` задаётся явно как IANA-зона. UI не берёт зону ноутбука за зону CSV.
Поддерживаемое мостом соглашение:
`provenance.timestamp_convention = "target_time = issued_at + horizon_step hours"`.
Команда должна подтвердить его или адаптировать мост к реальному соглашению.
В плоской таблице одной версии уникальны `(site_id, target_time)`, в replay —
`(run_id, site_id, target_time)`. Полная сетка проверяется по каждому часу и турбине.
Пропуски не заполняются, диапазон не исправляется через clip.

Для финального экспорта нужны доказательства от доверенного backend-моста:

```text
validation_summary.inputs_verified = true
validation_summary.model_verified = true
provenance.weather:
  source, version, available_at, data_kind = archived_forecast, synthetic = false
provenance.model:
  version, training_cutoff, normalization = 0_1, historically_eligible = true
```

`available_at` и `training_cutoff` не позднее исторического `issued_at`.
Время публикации, инициализации погодной модели и скачивания — разные сведения:
сегодняшнее `retrieved_at` не доказывает историческую доступность. Оценённую
доступность нельзя автоматически считать подтверждённой: нужна политика команды.

`verification_origin` назначает адаптер. Произвольный загруженный JSON всегда
`uploaded_unverified`, даже если содержит флаги `verified`. Синтетика всегда
блокируется программной проверкой итогового экспорта. Доверенный модуль backend
сам отвечает за достоверность свидетельств; UI не способен проверить провайдера
по одному самодекларированному полю JSON.

## Экспорт и состояние

`selected_csv(bundle, final=True)` повторно проверяет выпуск; `ExportBlocked`
содержит причины отказа. `final=False` — диагностическая выгрузка. `passport_json`
показывает очищенные метаданные. `replay_csv` сохраняет версии. `february_csv`
формирует отдельную сетку февраля с явным правилом `latest_available_before_target`;
применять его для сдачи можно после согласования с командой. Это внутренний CSV,
официальный формат организаторов не предоставлен. Выпуск на 48 часов в конце
февраля сохраняет мартовские часы; фильтрация февраля — отдельная операция.

Состояния сессии: idle/running/success/partial/error. Результат связан с параметрами
выбранного выпуска, а не с неотправленной формой. Ошибка нового запуска не выдаётся
за старый успех. Смена вкладок и скачивание не вызывают backend. Ошибка импорта
не включает demo. Сырые CSV не передаются LLM, динамические тексты не считаются HTML.

## Что необходимо от команды

Участник 1: реальные `site_id`, координаты и пути данных, соглашение о времени и
нормировке, версии модели/cutoff, независимый январский backtest с baseline,
целевыми парами и методикой. Дата создания файла модели не заменяет cutoff.

Участник 2: функции запуска/replay/обновления, архивная прогнозная погода и
доказательства её исторической доступности, реальные события, валидатор и правило
выбора версии на каждый целевой час. UI не создаёт собственный планировщик.

Пути артефактов, реальные метрики и команды backtest зафиксированы в [ML.md](ML.md).
Прямой `BackendAdapter` разрешает итоговый экспорт проверенного результата.
Загруженный JSON по-прежнему остаётся непроверенным файлом. Оба пути проверены
на настоящем финальном выпуске; синтетические данные не использовались для обучения.

## Артефакт январской проверки

`quality.load_backtest` принимает JSON в UTF-8. Сохранённый реальный результат
находится в `data/ml/january_backtest.json` и прошёл этот загрузчик:

```text
schema_version: 1
kind: january_backtest
data_mode: real_saved
timezone: подтверждённая IANA-зона
methodology: непустое описание проверки
provenance: {data_source: идентификатор/путь фактических наблюдений}
rows:
  run_id, site_id, issued_at, target_time, horizon_step,
  prediction, actual, model_version, training_cutoff
  baselines?: {название: числовой прогноз}
  actual_valid?: true/false
  prediction_valid?: true/false
```

Все даты со смещением; целевые часы только января 2026 в зоне артефакта.
Cutoff строго раньше проверочного выпуска. Разные выпуски на графике не
склеиваются. Ошибки считаются по конечным парам 0–1; недоступные факты не
заполняются нулями. Флаги валидности при наличии обязательны в каждой строке.

Агрегация UI — одинаковый вес каждой пары «выпуск / турбина / целевой час».
Отдельно показаны 1–24 и 25–48 часов. Для каждого baseline модель оценивается
на том же наборе доступных пар. При нулевой ошибке baseline процент улучшения
не вычисляется; ухудшение сохраняется отрицательным. UI проверяет структуру и
хронологию, но подлинность данных и независимость признаков подтверждает владелец.

## Реальный smoke-test

Проверенный локальный артефакт для Linux:

```bash
export WINDOPS_SMOKE_BUNDLE=data/forecasts/forecast-3bd7a5659d75a23ee6b9aea4/bundle.json
.venv/bin/python -m pytest -q tests/test_ui_smoke.py
```

Артефакт существует локально в `data/forecasts/`. Без переменной
этот тест явно пропускается. С её значением проверяются структура, время и
заявленные свидетельства реального архива; произвольный файл по-прежнему не
получает backend-доверие или право итогового экспорта автоматически.
