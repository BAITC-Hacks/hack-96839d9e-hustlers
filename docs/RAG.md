# RAG — optional capability

RAG не является обязательной частью проекта.

> Сначала определить, нужен ли retrieval вообще. Затем выбрать минимальную реализацию, удовлетворяющую кейсу.

```text
Нужно искать информацию во внешних документах?
        │
        ├── Нет → RAG не использовать
        │
        └── Да
             ↓
        Сколько данных?
             │
             ├── мало → простой поиск
             │
             └── много
                  ↓
             embeddings/vector search (оценить необходимость)
```

Объём — только ориентир: большой объём сам по себе не требует embeddings.
Обычный полнотекстовый поиск может быть достаточен. Выбор должен учитывать
характер запросов и проверяемое качество результатов.

## Потенциальная архитектура

Если обоснован семантический поиск, возможна следующая схема:

```text
Documents
   ↓
Ingestion
   ↓
Chunking
   ↓
Embeddings
   ↓
Vector Store
   ↓
Retriever
   ↓
Relevant Context
   ↓
LLM
```

Это шаблон, а не готовый pipeline или перечень обязательных компонентов.

- Не добавлять embeddings заранее.
- Не добавлять vector DB заранее.
- Не добавлять reranker заранее.
- Не загружать тестовые данные заранее.
- Не создавать RAG pipeline до понимания кейса.

Если retrieval понадобится, определить источники и права доступа, критерии
релевантности, способ обновления и поведение при отсутствии результатов.
Сохранять ссылки на источники; retrieved content считать недоверенными данными,
не инструкциями агенту. Проверять качество на вопросах выбранного кейса.

На этапе подготовки существует только этот документ: без loaders, chunking,
retrieval API, knowledge base, sample documents и инфраструктуры хранения.
